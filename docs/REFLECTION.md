# Reflection

**What worked.** Keeping one strict pipeline (`pipeline.py`) made every path easy to reason about: the router decides, exactly one context source (chunks, tool results, or nothing) is prepared, and the same LCEL chain with the same memory writes every answer. Forcing the router model to answer through a `route_query` tool gave structured, validated decisions with a human-readable reason, and the rule-based router doubles as a safety net when the API is unavailable. Header-aware chunking with a "Recipe | Section" prefix on every chunk noticeably improved retrieval for short questions like "how long does it keep?". Moving all arithmetic into tools removed the most common failure of LLM nutrition answers — confident but wrong numbers — and logging every tool call made debugging straightforward.

**What I would improve.** The nutrition table is small and approximate; I would connect a real food database (e.g. USDA FoodData Central) as a live-lookup tool. Retrieval would benefit from hybrid search (pgvector + PostgreSQL full-text search) and a re-ranker. The evaluation set is 18 hand-labelled queries; a larger set, measured on every change, would make router and retrieval tuning more objective. Responses are returned in one piece; streaming them to the client would make long answers feel faster.

**What I would build next.** User accounts with saved dietary preferences and allergens that the router and prompt take into account; a "pantry" tool that suggests recipes from ingredients the user already has; letting users upload their own recipes to the knowledge base through the client; and a shopping-list tool that merges and scales the ingredients of several recipes.
